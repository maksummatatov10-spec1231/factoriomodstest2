# 📚 Уроки моддинга: Fish Furnace — все ошибки и как их не повторять

> Этот документ — «память проекта». Каждая ошибка, допущенная при создании
> **Fish Furnace (v1.0.0 → v1.0.3)**, записана с причиной, решением и правилом,
> чтобы следующий мод создавался с первого раза без ошибок загрузки.

---

## 🔴 КРИТИЧЕСКИЕ ошибки (каждая ломала запуск игры)

### 1. `Unknown trigger effect item type: direct` (v1.0.0 → фикс в 1.0.1)

**Что было:**
```lua
damaged_trigger_effect = {
  type = "direct",                    -- ❌
  action_delivery = { type = "instant", ... }
}
```

**Причина:** спутал два разных уровня типов:
- `damaged_trigger_effect` — это **TriggerEffectItem** (союз конкретных типов: `create-entity`, `create-particle`, `play-sound`, `nested`, `script`, `set-tile`, `damage-entity`…). Типа `direct` там **нет**.
- `direct` / `instant` — это **TriggerDeliveryItem**, они живут ВНУТРИ `action_delivery` — а сама `action_delivery` существует только у триггеров `trigger`/`action` (напр. `created_effect` у капсул, `action` у мин), **не у** `damaged_trigger_effect`.

**Правильное (ванильный образец `hit_effects.rock()`):**
```lua
damaged_trigger_effect = {
  type = "create-entity",
  entity_name = "rock-damaged-explosion",
  offset_deviation = {{-0.5, -0.5}, {0.5, 0.5}},
  offsets = {{0, 1}},
  damage_type_filters = "fire"
}
```

**Правило:** любой `type = "..."` сверять со списком допустимых типов поля в
`https://lua-api.factorio.com/2.0.76/...` (для этого случая:
`types/TriggerEffectItem.html`). Работает и обратный поиск: если ошибка
«Unknown … type», открыть страницу типа и посмотреть дочерние элементы.

### 2. Звук `manual-repair.ogg` — файла не существует (v1.0.0 → фикс в 1.0.1)

**Что было:**
```lua
repair_sound = { filename = "__base__/sound/manual-repair.ogg" }  -- ❌
```

**Причина:** имя файла выдумано. В ванили `sounds.manual_repair` =
`sound_variations("__base__/sound/manual-repair-simple", 5, 0.5)` → реальные файлы
`manual-repair-simple-1.ogg … -5.ogg`. Ошибка «нет файла» вылезла бы следующей
после фикса №1 — поймал заранее.

**Правило:** пути к звукам/графике брать **только из ванильных исходников**:
`base/prototypes/entity/sounds.lua`, `base/prototypes/item_sounds.lua`
(репозиторий `wube/factorio-data`). Никогда не выдумывать имена файлов.

### 3. `Different frame counts (expected 1, but has 2) in animation layers` (v1.0.0–1.0.1 → финал в 1.0.3)

**Что было:** корпус `frame_count = 2` (моргание глаз), тень `frame_count = 1`.
Движок требует: **все слои одной анимации должны иметь одинаковое итоговое
число кадров** (`frame_count × repeat_count`).

**Решения (официальные):**
- Фрейм одного кадра повторить: `repeat_count = 2` — ответ разработчика posila
  (форум t=59604), и в доках `AnimationFrameSequence` пример
  «Single sprite that's repeated → `repeat_count = N`».
- Либо упростить: корпус вообще **1 кадр** (анимация — только рабочие
  визуализации: огонь 48 кадров, свет 48, ground-light 48 — они все едины по 48).

**Итог в моде:** корпус = 1 кадр; тень = 1 кадр; fire/light/ground-light = 48
кадров каждый (внутри `working_visualisations` согласованы).

**Правило:** `frame_count` одинаковый в слоях одной анимации; для повтора —
`repeat_count`; отдельная «мигающая» анимация = лишний источник конфликта,
если нет острой нужды — не делать.

### 4. Спрайт в 2 раза больше ванильного — `scale` (v1.0.2 → фикс в 1.0.3)

**Что было:** сгенерировал файлы в 2x-разрешении (302×292 вместо ванильных
151×146), но оставил `scale = 0.5` → экранный размер 151×146 (в 2 раза больше).

**Формула (подтверждена форумом t=106121):**
```
экранный размер = размер_файла × scale
ваниль:  151×146 × 0.5 = 75.5×73   (эталон!)
наши 2x: 302×292 × 0.25 = 75.5×73  ✅
наши 2x: 302×292 × 0.50 = 151×146  ❌ (было)
```

**Правило:**
- файл 1x (= ванильный размер) → `scale = 0.5`
- файл 2x (= ванильный размер × 2) → `scale = 0.25`
- файл 4x → `scale = 0.125`
- **всегда** пересчитывать `размер_файла × scale` и сравнивать с ванильным
  эквивалентом; тень/огонь/свет — та же логика (fire: 41×100@0.5 == 82×200@0.25).

## 🟡 Недочёты качества (не ломают, но заметны)

### 5. Спрайт выглядит «плоским 2D» (отмечено пользователем после v1.0.3)

**Симптом:** нет объёма/перспективы — печка читается как плоский рисунок.

**Причины (для исправления в СЛЕДУЮЩЕМ моде):**
- грани почти без градиентов: фасад/крыша/бок одинаково освещены → нет объёма;
- нет явной логики света (солнце сверху-слева): верхняя грань должна быть
  заметно светлее, боковая — темнее, передняя — средней;
- нет бликов на металле/чешуе и мягких внутренних теней (у кромок, под аркой);
- огонь/мягкие тайлы плоские — нужны блики на содержимом, лёгкое свечение;
- нет псевдо-перспективы «куба»: у ванильной печки видны 3 грани с сильным
  рендер-объёмом и фасками.

**План улучшения для следующего мода:**
1. Освещение: задать вектор света (напр. сверху-слева), яркость граней
   `верх = 1.25×`, `лицо = 1.0×`, `бок = 0.55×`.
2. Фаски/скругления рёбер через светлую кромку сверху + тёмную снизу.
3. Доп. объём: лёгкая «выпуклость» граней (радиальное затенение), тень под
   козырьками, металлические блики, крупные блики на чешуе.
4. Прозрачность/подсветка: glow + additive поверх огня, отражение в воде —
   уже было, но усилить перекрытие с фоном.
5. Итерации по превью на тайловом фоне 32px (как в игре) — сверять с ванильным
   силуэтом рядом.

### 6. Моргание глаз через 2 кадр корпуса — источник конфликта кадров
Лучше: моргание сделать эффектом (sticker-подобным) или отдельным слоем с
`repeat_count`, либо убрать. Для простоты — убрать.

### 7. Сдвиги (shift) огня/света придуманы с «глаз»
Исправлено на ванильные `util.by_pixel(-0.75, 5.5)` и `(0, 5)`.
**Правило:** `shift` брать из ванильного прототипа того же типа сущности.

## ⚙️ Процессные уроки / инфраструктура

### 8. Версии рассинхронизировались
Фикс v1.0.1: info.json = 1.0.1, а смоук-тест ждал 1.0.0 → тест падал.
**Правило:** при бампе версии обновлять **синхронно**: `info.json` +
`changelog.txt` + `README.md` + ожидание в `tests/`.

### 9. Git-особенности данной среды
- Нет `origin/<branch>` remote-tracking ref → обычный `git push origin branch`
  отклоняется (`stale info` / `non-fast-forward`), хотя локально история — над
  remote. Решение: `git push origin HEAD:refs/heads/<branch>` (при необходимости
  с `--force` после проверки, что remote-предок = `git merge-base --is-ancestor`).
- При сбросе среды локальная git-история начиналась с начального коммита
  (`a7eebe4`), но объекты remote были целы → восстановление: `git fetch origin
  <branch>` → `git diff FETCH_HEAD` → `git reset --soft FETCH_HEAD` → коммит
  изменений поверх.
- Перед коммитом: `python3 tests/smoke_test.py` — это обязательный шаг.

### 10. Структура zip
- Внутри архива **обязана быть папка** `mod-name_version/` (не файлы в корне!).
- Имя файла: `mod-name_version.zip`; имя папки = имени файла без `.zip`.
- Сборка: `zip -r -9 <name>_<version>.zip <name>_<version>/`.

### 11. Совместимость с пираткой 2.0.76
- `info.json`: `"factorio_version": "2.0"`, зависимости `base >= 2.0.0`.
- Использовать только API **2.0.x** — проверять по `lua-api.factorio.com/2.0.76/`,
  **не** использовать 2.1-фичи (`chain_probability` у quality, `recycler` как
  отдельный мод и т.п.).

### 12. Автотесты должны ловить классы ошибок (что уже добавлено)
В `tests/smoke_test.py` (LuaJIT) проверяется:
- белый список типов `TriggerEffectItem` (ловит «Unknown … type»);
- существование всех путей `filename` (ловит «нет файла»);
- одинаковый `frame_count × repeat_count` по слоям анимации;
- `scale = 0.25` для 2x-файлов (ловит «огромный спрайт»);
- кросс-связки: item↔entity↔recipe↔technology, локали, info.json.

## 📌 Итоговое резюме для следующего мода

1. **Источник истины — ваниль + официальные доки 2.0.76.** Любое поле,
   любой тип, любое имя файла — сначала смотреть там, потом писать.
2. **Графика: считай пиксели.** `файл × scale = экран`. Проверяй превью
   на тайловом фоне рядом с ванильным спрайтом.

   `working_visualisations`.
4. **Объём в спрайтах** — приоритет улучшения: 3 грани с разной яркостью,
   фаски, блики, внутренние тени (подробный план в разделе 5).
5. **Тест — перед каждым коммитом.** Смоук-тест ловит классы прошлых ошибок.
